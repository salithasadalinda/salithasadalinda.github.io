ESP-32 Camera Streaming: What I Learned

Jul 20, 2026 · Firmware · ESP-32

Streaming video from an ESP-32 CAM sounds simple — it isn't. Memory is tiny, the board runs hot, and a naive server makes everything crawl. These are the lessons from building a camera server on the Xiao ESP32S3 Sense, AI-Thinker ESP-32 CAM and ESP-EYE, and from running on-device ML on the same boards.

Pick the board for the job

All three use the OV2640 (2 MP), but they are not equal. The Xiao ESP32S3 Sense is the one I keep reaching for — dual-core 240 MHz, 8 MB PSRAM, 8 MB flash, BLE 5.0, a built-in PDM mic and Type-C. The AI-Thinker CAM is cheapest but has no USB (UART only) and only 4 MB PSRAM. ESP-EYE has a display and face detection built in but costs the most. For ML work the ESP32S3's larger PSRAM and faster cores matter most.

They get hot — plan for cooling

The Xiao ESP32S3 genuinely gets hot while streaming MJPEG. I added a copper heatsink (not aluminium) plus a 3D-printed cooling contraption with a fan, mounted on a modular gorilla-arm screw adapter. Two things I got wrong the first time:

  • Aluminium heatsinks are not enough — copper draws the heat out properly.
  • Power the fan from its own source, not the same VBUS as the board. Sharing the rail degraded performance.

Camera settings that actually matter

One preprocessor macro selects the board — uncomment only one camera model. For a stable stream the key settings were: 

config.frame_size = FRAMESIZE_QVGA;   // 320x240
config.jpeg_quality = 24;             // 0-63, lower = higher quality
config.fb_count = 2;                  // double buffering, smoother stream

s->set_brightness(s, 2);              // -2 to 2
s->set_contrast(s, 1);
s->set_saturation(s, 1);

Double buffering is the big one — capture and serve must run asynchronously, otherwise the camera stalls while a client downloads a frame.

Memory is the real constraint

A typical boot leaves about 229 KB free heap and ~8.3 MB free PSRAM. A stream plus a web UI eats that fast. Serve static assets gzipped straight from flash instead of RAM. I compress the whole frontend into a C header (gzipped_assets.h) with a build script, and register async routes for it — faster boot, fewer bytes in RAM.

WiFi that survives a reboot

Config lives in LittleFS (wifi_credentials.json, ei_config.json). If no saved network is reachable, the board drops into AP mode with a captive portal, so setup needs no serial terminal. Multiple networks are stored and persist across reboots — the same device moves between sites without reconfiguration.

Running ML on the same camera

Object detection (Edge Impulse FOMO) and TinyML image classification run on these boards. Lessons:

  • The tensor arena must live in PSRAM — heap_caps_malloc(..., MALLOC_CAP_SPIRAM). Without OPI PSRAM enabled in board settings the model won't even load.
  • FOMO needed the arena size roughly doubled (e.g. 182 KB → 365 KB).
  • The Xiao camera auto-detects as OV3660, not OV2640 — trust the driver's detection.
  • Reference kernels took ~4.6 s per frame. ESP-NN kernels using the ESP32S3's MAC16/PIE instructions got inference to ~147 ms — about 31× faster, and fast enough for real-time classification.
